The decision story behind a Thai–Lao license plate recognition system — from six failed eras to an architecture that actually ships.

Prologue · the starting point

Where we started — not “let’s build an AI model”

2025-12-04

First commits: first commit → preprocess fix → train fix → api add

A prototype reader plus a FastAPI service. We did not yet know where the real problems were hiding — this was pure exploration.

The actual business problem: CCTV at gates and checkpoints must read Thai and Lao plates, store searchable history, and — critically — ship inside the customer’s existing system, which is written in C# (.NET).

What the system must do

  • Take an image or an RTSP stream → detect the plate in a real street scene
  • Rectify the plate, then separate the character row from the province row
  • Read both the “series–number” and the “province” correctly
  • Record in real time and feed analytics (Firestore + BigQuery)

Working rules this project has followed from day one

  • Config-driven — important knobs live in config, not scattered in code
  • Validate + regression-check before every delivery
  • Test first, then run the full job
  • Always report which files changed and how to verify

That discipline is exactly why Acts V–VII have real measured numbers to tell.

Prologue · the compass

Three constraints that decided everything else

The most accurate model in the world is worthless the moment it violates one of these three. This is what makes the project choose differently from everyone else.

① Commercial license

The customer is industrial → no AGPL, no royalty.

Consequence: Ultralytics YOLO (AGPL-3.0) is allowed only as a benchmarking tool; anything in the served weights must be MIT / Apache-2.0 / BSD-3.

D-FINE = MIT · RF-DETR = Apache-2.0 · MobileNet/ResNet = BSD-3

② CPU only, no GPU

Target runtime is Cloud Run / an edge box — no GPU available.

Consequence: the ~75–95 ms per-image budget eliminates large transformer detectors instantly (84–108 ms per stage).

FORCE_CPU=True · warmup at startup

③ Must run on C# .NET

Every model must export to ONNX (Opset 18) and run through Microsoft.ML.OnnxRuntime + OpenCvSharp4.

Consequence (the big one): anything needing a custom C++ operator dies right here. Luckily it died during experiments, not during delivery.

docs/csharp_integration_guide.md · no Python needed on the customer’s machine

ACT I

The plate was never straight

This act asks: “why do we still misread characters that look perfectly clear?”

The first era assumed “find the plate → crop → feed OCR”. It did not take long to learn that nearly half the errors were not the reader’s fault — they were caused by the geometry of the image we were feeding it.

Act I · era 1

❌ Era 1 — plain AABB, then crop straight out

What we did

An axis-aligned detector returns a rectangle → expand it slightly → crop → send to OCR.

What we found

Whenever the camera is mounted at an angle or the car is turning, the plate becomes a trapezoid: characters are stretched and no two are the same height.

> 40%
misread rate on angled plates
2026-09-03

Commit: feat: implement perspective transform pipeline

That day we stopped “cropping” and started “transforming the viewpoint” — the first architectural turning point.

Lesson from this act

Before changing the model, check whether the image you feed it is still the problem.

ACT II

The path that looked best was the dead end

This act asks: “why can a model that is accurate in a notebook never reach the customer?”

The answer is Rotated NMS — a custom C++ operator that standard ONNX Runtime does not have. The OBB model worked beautifully in PyTorch and broke at export. That was the day the C# constraint became the narrator of this whole story.

Act II · era 2

❌ Era 2 — one-stage Rotated Bounding Box (OBB) / segmentation

Why it looked good

  • Rotatable boxes → handle angled plates in a single model
  • Segmentation gives a plate mask → rectify directly from it
  • “One model, done” reads as simpler

The two walls we hit

  • Slow on CPU: ~90–120 ms per image, over the real-time budget
  • Export refused: ONNX needs Rotated NMS as a custom C++ operator, which standard ONNX Runtime does not provide

→ barely runnable from C# / .NET and fragile in deployment (commits fcf9857, efc2e47)

The painful truth: we burned time on a route that had good accuracy but was not shippable. Had we started from the deployment constraint instead of the benchmark, we would never have spent that month.
Lesson from this act

Try the export and run it from the target language on day one — not after training finishes.

Act II · the fix

If ONNX Runtime cannot do Rotated NMS, then we rotate the image with OpenCV — and let the model do only what exports everywhere: regress four points.

ACT III

Reading the whole plate at once did not work

This act asks: “why did the province name end up inside the plate number?”

Thai plates have two rows (series–number on top, province below) and trucks have a dash. Fed the whole plate, the OCR “reads it as one sentence” and the rows bleed into each other.

Act III · era 3

❌ Era 3 — whole-plate OCR with no component split

Symptoms we saw

  • The province name leaked into the plate number
  • Top and bottom rows swapped places
  • Truck plates with a dash → the model tried to read the dash as a character

Fix: Model 2 (component detector)

Add a stage that does exactly one thing — separate the plate_char zone from the province zone — then let each specialist model read its own part.

commit 2026-09-04 “add code for model 2 plate and province charactor”
This was the first time we changed our way of thinking, not our model. We stopped trying to make one model smarter and started giving each job to the right stage — which fixed something that adding capacity never could.
Lesson from this act

When one model is asked to do two jobs at once, its failures become too tangled to diagnose.

ACT IV

The era the model invented answers

This act asks: “why could the system confidently read things that are not on the plate?”

When a late-stage model is required to answer, small errors get promoted into plausible-looking text. That is worse than saying “I cannot read it”, because nobody knows it is wrong.

Act IV · three failures

Eras 4, 5 and 6 — different symptoms, one root cause

Era 4

❌ Trusting the DLT top banner code (two digits beside “THAILAND”)

The digits are tiny and usually pierced by the mounting screw → 70 (Ratchaburi) read as 55 (Nan), and then it overrode a correctly read province name.

The interesting part: commit 09-09 implement DLT truck province code extraction, then 09-17 remove DLT truck extraction logic — we built it, then we deleted it.

Era 5

❌ Blind CTC insertion — filling missing boxes without checking

Screws and reflective frames got hallucinated as digits: real plate กย 588 became 5กย 4588. A truck plate 70-1737 had its dash read as a consonant → 70ษย7ม, which is plainly illegal.

Era 6

❌ Merged boxes swallowing characters + an imbalanced classifier

Adjacent characters (97) were predicted as one wide box (w > 1.6 × median) and NMS then swallowed the two real children. A single-letter plate ณ 4100 was hallucinated into 74-0001.

The shared pattern: a late stage had real power to override earlier results, with no check on whether the output was even possible under plate grammar.
Act IV · the fixes

✅ Era 7 — teaching the system what is impossible

1 · Subsumed composite box filter

Detect abnormally wide boxes that contain two smaller boxes → drop the merged box so both real characters survive.

commit 09-21: add greedy NMS and wide box splitting

2 · DLT syntax placement guard

has_invalid_thai_consonant_placement() locks private-plate grammar: no consonant after a two-digit number, and no \d[consonant]\d{4} shape.

3 · Protected sequence reconciliation

Protects genuine Thai consonant plates like ณ 4100 or ผว 7697 from being overwritten by a hallucinated truck reading.

4 · Autocontrast normalization

Expands the dynamic range of shadowed character crops before classification — related to commit 09-09 add low-light CLAHE enhancement.

Lesson from this act

A system that must always answer will hallucinate — it needs both rules that say “impossible” and a way to say “I do not know”.

ACT V

The turn: stop tuning models, start auditing data

This act asks: “if the architecture is already right, why is accuracy still stuck?”

After we had fixed the architecture, the model still failed on the same classes over and over. So we audited the house we had built — and found four uncomfortable facts.

Act V · the audit

What the dataset audit found — and why it changed everything

① Class imbalance beyond imagination

Character training set: digits had ~180–214 crops per class, while ง ฟ ธ ค ฐ น พ ป had exactly 1 crop — a 200 : 1 ratio.

Province training set: Bangkok had 470 crops versus 1 crop for a small province — 470 : 1.

→ Rare classes survived by “remembering the picture”, not by learning the province itself.

② Train/serve crop mismatch

The original dataset was hand-boxed on Roboflow, while production used its own crop rules (insets / padding / min-y gating).

→ The province model looked great in-dataset but failed on real street plates, because the distributions differed. The root cause was that we built our data differently from how we use it.

③ Hidden split leakage

Frames from the same capture second (the same car in the same video) sat in both train and valid · byte-identical province crops were on both sides · per-crop sampling scattered one plate’s crops across splits.

→ The old validation accuracy was inflated and not comparable at all.

④ Junk that the classifier was forced to name

Dash slivers, plate-edge fragments and screws survived NMS, and the classifier has only 50 classes (digits + consonants, no “junk”) — so it was forced to pick a digit.

→ This is the origin of the extra digits and distorted shapes seen on screen.

Act V · the fix

Building a three-step data pipeline you can trust

Step 1 · Extract

extract_recognition_crops_v2.py

Crops using exactly the serve rules (not hand-drawn boxes) plus a manifest.csv recording the provenance of every crop.

Directly fixes finding ②

Step 2 · Split

split_recognition_dataset_v2.py

Source-image grouped splitting — all crops of one car or one video stay on the same side.

Directly fixes finding ③

Step 3 · Curate

curate_recognition_v2.py

Inspect and correct label errors safely, always in sync with the manifest — never editing stray files.

commit 2026-09-26

Then we added data — in two ways that do not cheat

  • Self-labeling harvest: run the same pipeline as serve (M3A box → geometric filter → classifier) over new real images, keeping only conf ≥ 0.70, with full provenance in the manifest.
  • Augmented-variant balancing: fill thin classes with rotated / scaled / jittered / blurred variants — not by duplicating the same image.

Why not just copy images until the counts match?

Duplication makes a small class overfit one picture without adding anything for the model to learn — training numbers improve while generalization gets worse.

That is why we used WeightedRandomSampler plus class weighting at the loss instead of adding files.

Lesson from this act

Data diversity fixes what architecture and hyper-parameter tuning cannot.

Why “50% duplicates” is not as bad as it looks

The duplicates are removed by charbox_greedy_nms (IoU 0.35), leaving 1–3% — whereas a missing box is unrecoverable.

A case study in how a single aggregate metric is never enough: you must ask which kind of error can be repaired.

Act VII · honesty

Four limitations you must read before quoting these numbers

① Resolution of the evaluation set

97% of v5i (train and valid alike) is 192×99 px (Roboflow thumbnails) — the plate is only ~50 px wide and the province strip ~15 px tall.

→ 91.89% is a low-resolution stress test, not what production should expect (real images are 4–10× sharper).

② The whole-plate ground truth is a pseudo-label

full_ocr_text comes from candidates_metadata.csv, which is model output (it has a confidence column and auto_* filenames).

→ 51.60% and 84.88% include the GT’s own mistakes (e.g. GT ฆช 8734 where ฆ barely exists on real plates). The true figures should be higher — nobody knows by how much until a human-verified set exists.

③ In-dataset 100% still has leakage

province 62/77 classes (81%) and char 46/48 (96%) share source images between train and valid.

Some classes have only 1–5 unique sources — 6 classes have exactly one (31 crops = one photo + 30 augmentations) → 100.00% on valid is optimistic by construction.

④ No production-resolution number exists yet

Because of ① and ②, we do not yet have the figure needed to decide config or model choice.

That is exactly why experiment E1 — a real-photo set with human-verified GT — has to happen before anything else.

Why publishing limitations is a strength, not a weakness: an honest number that says where it applies can be audited and built upon. A flattering number with no provenance cannot — and it breaks the moment the customer uses it.
Act VII · the last bugs

Two production cases that sent us back into the fusion logic

Case A · a plate read with a duplicated character

The box stage saw 2 ถ ล [ล] 1 2 3 8 (two ล) while CTC read 2ถล1238. difflib matched the longest common run ล1238, so the extra ล slipped past both the replace-tail and the equal-block path without hitting the syntax guard.

2ถลล1238 Custom / Unstandardized → 2ถล 1238 NCC NNNN · private car

Fixed with a final syntax repair inside align_and_fuse_thai_sequences() that strips box-extra characters making the pattern illegal after fusion completes · commit 09-28.

Case B · the truck refiner overwriting a valid letter plate

For 5ศ 7856, fusion internally returned 57856, but a call-site guard saw the plate had a consonant in a legal position and that is_valid_plate passed → the truck refiner was not allowed to overwrite it.

5ศ 7856 NC NNNN · trailer / special

Re-checked with no regression: 1กข 1234, กข 4962 and 83-4203 behave as before · commit 09-28 fix: prevent truck refiner from overriding valid letter plates.

Technical debt still open: has_invalid_thai_consonant_placement() rule 4 still forbids the NC NNNN shape, while is_valid_plate() accepts it (PATTERN_NC_NNNN). The two functions contradict each other and are only papered over by the letter-plate guard — it works, but on an assumption nobody has confirmed.
EPILOGUE

Six principles this project produced

And they explain why every library choice looks the way it does

1 · Deployment constraints decide the architecture

“Must just work from C#/ONNX” eliminated OBB and large transformers before we could waste more time on them.

2 · License is an engineering constraint, not paperwork

Discovering an AGPL dependency after the model works means rebuilding the system — so we chose MIT/Apache/BSD on day one.

3 · Splitting the job beats growing the model

The M2 component detector solved what extra capacity could not — exactly as the 2-stage keypoint solved what OBB could not.

4 · A model that must always answer will hallucinate

Eras 4–6 are the price of “never say I don’t know” → syntax guards, a junk class, and an abstain path are needed.

5 · When the dataset is the bottleneck, data-centric wins

Harvest + balance + leak-free split took character accuracy from 96.71% to 99.71% without touching the architecture.

6 · An honest number beats a flattering one

Writing “91.89% measured at 192×99 with pseudo-label GT” next to the figure tells us what to do next. An unqualified 100% tells us nothing.

Epilogue · we need confirmation

Four questions only the system owner can answer

These are policy and product decisions, not technical ones. The code can go either way — but we must know whether the system is allowed to say “I don’t know”.

① Is the NC NNNN plate legal?

e.g. 5ศ 7856, 8ว 7687
If yes → fix has_invalid_thai_consonant_placement() rule 4 to agree with is_valid_plate().
If no → add a guard so a consonant-bearing box is never recovered (today the code assumes “yes”, via the letter-plate guard).

② May the system abstain?

If the downstream workflow requires an answer every time, we must switch to prior correction instead — nudging scores away from data-poor classes while still answering.

③ Is replacing autocontrast with CLAHE acceptable?

CLAHE (clipLimit 2.0, tile 4×4) or character-ROI-masked autocontrast may beat global autocontrast, which can sink characters when the crop includes a bright plate border — but choosing it means retraining the whole set to keep the contract.

④ Is there budget for ~1,000 more real images?

For the 36 thin province classes (the worst 12 first). If not, we must accept a lower ceiling and lean on abstain instead.

Why ask before building: all four decide whether the system should “always guess” or “sometimes admit it does not know”. Both are implementable — they are not interchangeable.
Closing

The whole story in five lines

Synopsis

  1. Started from a CCTV problem reading Thai–Lao plates that had to be embedded in a C# system.
  2. Six failed eras — each one lost to a constraint (license / CPU / ONNX), never to accuracy.
  3. Fixed it by giving each job to the right stage (2-stage keypoint, M2 component detector, dual-engine OCR).
  4. Then found the real bottleneck was the data — so we built a leak-free data pipeline plus harvest and balancing.
  5. Measured honestly on real images, which produced both free wins (upscaling) and the v6 backlog.

What is ready today

  • Latency: ~75–95 ms end-to-end on a normal CPU
  • Models: every stage exports to ONNX (Opset 18) with a ready C# (.NET) guide
  • License: MIT / Apache-2.0 / BSD-3 throughout — 100% commercial
  • System: FastAPI + per-stage debug dashboard + Firestore/BigQuery + Cloud Run
  • Data: a retraining pipeline where every crop is traceable
What to tell the customer plainly: the system is production-ready as engineering — but the accuracy figures that would justify pricing or an SLA must wait for a benchmark at production resolution with human-verified GT (E1). What we have today is 91.89% province and 51.60% whole-plate, measured on 192×99 images whose GT still contains noise.

Appendix B

The preprocessing contract — four special techniques

1 · Smart padding homography crop

Expand the M1 bounding box by a 12% margin before the corner regressor so no plate corner falls outside the image.

2 · Four-point clockwise quad sorting

Order corners as TL → TR → BR → BL using x+y and y−x before cv2.getPerspectiveTransform — prevents swapped corners from warping the image.

3 · Grayscale smart-resize with ambient background filling

Black padding confuses the province model into reading it as text, so we read the median colour of the four corners (np.median(corners)) and use it as the canvas background.

Thai (256, 80) · Lao (256, 64) · norm 0.5/0.25

4 · Serve-geometry upscale (Stage 2 / 3A)

Rectified plate 320×160 → 1280×640 before M2, then boxes are divided back per axis. Character row → 2088×560 before the char-box detector.

All of it is STRETCH only — no letterbox/pad, because the models trained with stretch

Libraries used in preprocessing

  • OpenCV (cv2) — decoding, BGR→RGB/LAB, CLAHE, perspective transform, deskew
  • NumPy — corner coordinate math, vectorization, box sorting, NMS
  • Pillow — high-quality resize (BICUBIC), grayscale, dynamic canvas padding
  • TorchVision Transforms — normalization and tensor formatting

Appendix C

Augmentation — what we use, and the axes still missing

In use today

  • Province (train_grayscale_province_thai.py): RandomAffine 5°, translate .03/.04 · ColorJitter .3 · RandomAdjustSharpness 2.0 (p=.5) · RandomAutocontrast (p=.5)
  • Character (train_character_classifier.py): RandomAffine 6° scale .95–1.05 · ColorJitter .35 · RandomGrayscale .15 · RandomPerspective .12 (p=.3)
The gap: no Gaussian blur · no motion blur · no scale degradation · no perspective for province — precisely the axes that match the measured domain gap.
